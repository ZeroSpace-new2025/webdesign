# M2 订单与交易核心 · 实现路径

> 负责“怎么买”：订餐时间窗口、下单与改单、一人一天一单、个人历史与月度消费、经理作废违规订单。
> 需求映射：`root_demend.md` 功能 3（截止前点餐、一人一单、经理删单）、功能 6（员工月度汇总与打印）；
> 页面设计见 `demand.md` M2 章节。

## 二、数据模型

| 表 | 关键字段 | 约束/索引 | 说明 |
| --- | --- | --- | --- |

## 三、实现路径

### 1. 查询时间窗口

```
GET /api/v1/order/windows 或 点位页加载
  → OrderService.getWindow(LocalDate)
  → ServiceWindowService.get(date, null, deptId)   // M3 契约：唯一时间来源
  → ServiceWindowVO(cutoffTime, deliveryStartTime, canOrder, canDeliver, serverTime)
```

### 2. 下单（核心链路）

```
页面 POST /order/submit（无既有订单时） / API POST /api/v1/order/orders + 请求头 Idempotency-Key
  → OrderPageController.submitOrder / ApiOrderController.submit
  → OrderService.submit(OrderSubmitCmd)
  → OrderServiceImpl
       1) 幂等键必填；orderFormRepository.findByIdempotencyKey 命中 → 直接返回既有订单（不重复下单）
       2) authService.checkPermission(userId, ORDER_SUBMIT) → 无权限 40300
       3) assertWithinWindow(today, deptId)
            → ServiceWindowService.get(...).canOrder == false → 42201 OUT_OF_TIME_WINDOW 已过订餐截止时间
       4) assertNoActiveOrderToday(userId, today)
            → countByEmployeeIdAndOrderDateAndStatusIn(PENDING, VALID) > 0 → 42202 RULE_VIOLATION 一人一天一单
       5) requirePublishedMenu(today) → MenuService.getCurrent(today) → 无菜单 40902
           · 请求里的 menuId 与当前菜单不一致 → 40902「菜单已更新，请刷新」
       6) appendDetails：按菜单项快照写入 order_detail（菜名/分类/单位/单价/数量/金额）
       7) recalculateTotal → order_no = yyyyMMdd + 4 位当日流水（nextOrderNo 取当日最大单号 +1）
       8) save → 发布 OrderCreatedEvent
            → 事务提交后 M3 的 OrderCreatedListener 重算当日 daily_statistics 快照
              （监听器另开 REQUIRES_NEW 事务；失败只影响派生快照，不影响已经落库的订单）
  → 返回 OrderVO（含明细）
```

### 3. 改单（截止前）

```
页面：/order/create 已有今日订单 → 再次提交走 modify；API PUT /api/v1/order/orders/{orderId}
  → OrderService.modify(orderId, OrderModifyCmd)
  → OrderServiceImpl
       1) requireOrder + assertOwner（只能改自己的）
       2) assertWithinWindow（截止后不可改）
       3) assertEditable：仅 PENDING 可改（VALID 已确认后不可改）
       4) @Version 校验（页面回传 version，冲突 40902）
       5) requirePublishedMenu + indexMenuItems → clearDetails → 重新 appendDetails（整体替换明细）
       6) recalculateTotal → saveAndFlush → OrderUpdatedEvent(MODIFIED)
```

### 4. 取消（员工本人，截止前）

```
POST /api/v1/order/orders/{orderId}/cancel 或 页面 POST /order/{id}/cancel
  → OrderService.cancel(orderId, reason)
  → OrderServiceImpl：assertOwner → assertWithinWindow → assertEditable
  → order.markCancelled(reason ?: "员工取消") → status=CANCELLED + cancel_reason
  → OrderUpdatedEvent(CANCELLED)
```

### 5. 作废（经理删单，逻辑删除留痕）

```
页面 POST /order/manage/{id}/invalidate 或 API DELETE /api/v1/order/orders/{orderId}
  → OrderManagePageController.invalidate / ApiOrderController.invalidate
  → OrderService.invalidate(orderId, reason)
  → OrderServiceImpl
       1) reason 必填
       2) authService.checkPermission(userId, ORDER_INVALIDATE) → 只有经理可以作废
       3) 已作废订单再作废 → 40902
       4) markInvalid(userId, reason)：status=INVALID + invalidated_by/invalidate_reason/invalidate_time
       5) 发布 OrderUpdatedEvent(INVALIDATED)
       6) 返回审计号 AUDIT-{orderId}-{userId}
```

> 作废是**逻辑删除**：不物理删行；作废后不再占用“一人一天一单”名额，也不参与聚合、配送与报表。

### 6. 订单查询（经理/财务）

```
GET /api/v1/order/orders
  → OrderQueryService.page(OrderQuery)
  → OrderQueryServiceImpl.page
       · 非经理/财务：强制 employeeId = 当前用户（忽略请求里伪造的 employeeId）
       · buildSpecification：员工/部门/日期区间/状态；includeInactive=false 时默认只查 PENDING/VALID
       · Sort created_at DESC → toPageResult → enrichEmployee（UserService.listByIds 补姓名/部门）
```

页面 `/order/manage`（经理）：`OrderManagePageController.page` 固定 `includeInactive=true`、单页 200 条，
日期区间默认“今天”，支持状态筛选，行内提供「作废原因 + 作废」表单。

### 7. 个人历史订单

```
GET /api/v1/order/orders/history 或 页面 /order/mine
  → OrderService.pageHistory(OrderHistoryQuery) → OrderQueryService.pageHistory(employeeId, DateRange, PageQuery)
  → OrderQueryServiceImpl.pageHistory：本人或经理/财务；includeInactive=true（历史里要能看到已取消/已作废）
  → 页面同时算当月消费合计（不含取消/作废）并展示今日订单（可取消/去改单）
```

### 8. 个人月度消费统计（可打印）

```
GET /api/v1/order/orders/history/monthly-summary 或 页面 /order/monthly
  → OrderStatisticsService.monthlySummary(employeeId, month)
  → OrderStatisticsServiceImpl
       1) 本人或经理/财务，否则 40300
       2) loadMonthlyOrders：按月取该员工 PENDING/VALID 订单（含明细）
       3) 按分类、按菜品聚合 quantity/amount；分类占比 = 金额 / 总额（保留 1 位小数）
  → 页面 MonthlySummaryVO + 当月订单列表（OrderService.pageHistory）
  → 「打印 / 另存 PDF」走 style.css 的 @media print（隐藏导航、按钮、筛选）
```

### 9. 导出个人消费明细

```
GET /api/v1/order/orders/history/export?format=XLSX|CSV
  → OrderStatisticsService.exportHistory(employeeId, month, ExportFormat)
  → TabularExport.xlsx / csv（PDF 未引入生成库 → 40001）
```

## 五、权限与角色

| 能力 | 权限点 | 角色 |
| --- | --- | --- |
| 点餐、改单、取消、看自己的历史与月度汇总 | `order:submit`（15） | 全部预置角色（需求：任何用户都拥有普通员工权限） |
| 订单管理页、作废违规订单 | `order:invalidate`（16） | MANAGER |
| 查询全部订单（接口层 `GET /orders`） | `order:view:all`（17） | 实际按**角色**判定：MANAGER、FINANCE（`OrderQueryServiceImpl.canViewOthers`）；其他角色（含持有该权限点的 KITCHEN_SUPERVISOR）只能查自己 —— `@RequiresPerm` 不拦这个接口，行级过滤在 service 里做 |

> 注：`GET /api/v1/order/orders` 没有 `@RequiresPerm`，`page` 内部对非 MANAGER/FINANCE 强制
> `employeeId = 当前用户`，所以“员工只能查自己”是靠 service 行级过滤保证的，不靠注解。

## 六、跨模块依赖与事件

| 方向 | 对象 | 用途 |
| --- | --- | --- |
| 调用 M3 | `ServiceWindowService.get(date, scope, deptId)` | 订餐截止时间（唯一时间来源） |
| 调用 M1 | `MenuService.getCurrent(date)` | 当日已发布菜单与快照价（唯一取价入口） |
| 调用 M4 | `AuthService.checkPermission`、`UserService.listByIds` | 权限复核、补员工姓名/部门 |
| 发布事件 | `OrderCreatedEvent` | M3 `OrderCreatedListener`（AFTER_COMMIT + `REQUIRES_NEW`）→ `refreshDailyStat(orderDate)` 重算当日总括订单快照；M4 报表侧暂无订阅方 |
| 发布事件 | `OrderUpdatedEvent(MODIFIED/CANCELLED/INVALIDATED)` | M3 `OrderUpdatedListener` 同样重算当日快照；M4 报表侧暂无订阅方（报表按需手动刷新） |

> 事件订阅是**跨模块但非注入依赖**：监听器只依赖 `BlanketOrderService` 接口，M2 不感知订阅方；
> 订单事务提交后监听器才执行，因此订阅方失败不会回滚已下的单。

## 七、关键不变量

1. **一人一天一单**：服务层 `countByEmployeeIdAndOrderDateAndStatusIn(PENDING, VALID)` + 数据库部分唯一索引兜底。
2. **截止时间唯一来源**：不读配置项，一律 `ServiceWindowService.get(...)`。
3. **快照**：`order_detail` 全字段快照（菜名/分类/单位/单价/数量/金额），菜单调价不影响历史订单。
4. **幂等**：`Idempotency-Key` 必填，命中既有键直接返回原订单。
5. **作废留痕**：`status=INVALID` + 作废人/原因/时间，不物理删除。
6. **单号**：`yyyyMMdd + 4 位当日流水`；高并发撞号由唯一约束拒绝（已知缺口，见 AGENTS 6.6）。
