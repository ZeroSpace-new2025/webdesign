# M3 运营与履约系统 · 实现路径

> 负责“怎么做、怎么送”：订餐截止后聚合总括订单（生产单），配餐开始后按员工生成并打印配送单，维护时间窗口配置。
> 需求映射：`root_demend.md` 功能 4（截止后打印总括订单供厨房备料）、功能 5（配餐开始时间后批量打印配送单，
> 之后即可订次日）；页面设计见 `demand.md` M3 章节。

## 三、实现路径

### 1. 时间窗口读取（全系统唯一时间来源）

```
GET /api/v1/operation/configs/service-window 或 各页面加载
  → ServiceWindowService.get(date, scope, deptId)
  → ServiceWindowServiceImpl
       1) resolveConfig：按 effective_from 倒序取生效配置，DEPT（指定部门）优先于 GLOBAL
       2) 无配置 → 回退 ServiceWindowProperties（app.service-window.default-*，默认 09:00 / 11:30）
       3) canOrder = now < cutoff_time；canDeliver = now >= delivery_start_time
  → ServiceWindowVO(configId, cutoffTime, deliveryStartTime, effectiveFrom, scope, deptId, serverTime, canOrder)
```

### 2. 时间窗口维护

```
页面 POST /operation/configs/service-window 或 API POST/PUT /api/v1/operation/configs/service-window[/{id}]
  → ServiceWindowService.create / update
  → ServiceWindowServiceImpl
       1) validate：时间非空、cutoff < deliveryStart、作用域合法、DEPT 必须有 deptId
       2) create 校验同作用域 + 同生效日期不重复（40901）
       3) save → 立即生效（M2/M3 每次判定都重新读库，无缓存需要刷新）
```

### 3. 总括订单聚合（截止后，幂等）

```
定时任务 09:00 OrderWindowCloseJob → 发布 OrderWindowClosedEvent（无事务上下文）
  → OrderWindowClosedListener（@TransactionalEventListener AFTER_COMMIT + fallbackExecution=true，
    且方法上 @Transactional(REQUIRES_NEW)）→ BlanketOrderService.aggregate(date, true)
页面「手动聚合」POST /operation/blanket-orders/aggregate 或 API POST /api/v1/operation/blanket-orders/aggregate
  → BlanketOrderService.aggregate(date, force)
  → BlanketOrderServiceImpl
       1) requireWindowClosed(date)：取 ServiceWindowService.get(...).cutoffTime 与服务器时间比较，
          当天早于截止时间 → 42201 OUT_OF_TIME_WINDOW；未来日期同样拒绝（历史日期允许补聚合）
       2) force=false 且已有 daily_statistics → 直接返回既有快照（幂等，不覆盖）
       3) rebuild(date)：
            · OrderQueryService.listValidByDate(date) → 当日 PENDING/VALID 订单（含明细快照）
            · 按 分类 + 菜品 聚合 quantity / amount / orderCount
            · 覆盖写 daily_statistics（先清空 statistics_item 再写，statistics_date 唯一）
       4) 返回 DailyStatVO(totalOrders, totalAmount, items[])
```

**两个容易踩的 Spring 事务坑（已修复，改监听器时别再踩）**：

1. `@TransactionalEventListener` **默认在事件发布方没有事务时静默跳过**。定时任务不是
   `@Transactional` 的，所以监听器必须显式 `fallbackExecution = true`，否则 09:00 的自动聚合
   从来不会执行（事件发了、监听器不跑，没有任何报错）。
2. `AFTER_COMMIT` 阶段原事务已提交，但事务同步器仍挂在当前线程上；此时以默认 `REQUIRED`
   传播进入会“加入”这个已完成的事务而不开新事务，JPA 抛
   `TransactionRequiredException: No active transaction`，异常被事务同步器吞掉只留一行 ERROR 日志。
   监听器方法必须标 `@Transactional(propagation = REQUIRES_NEW)`。

窗口关闭时的聚合传 `force = true`：截止前订单变更已经写过一份快照，
幂等分支会直接复用，只有覆盖重算才能保证“截止这一刻”的生产量是完整的。

### 4. 厨房备料页 / 历史快照

```
GET /operation/blanket-orders（页面）→ BlanketOrderPageController.page
  → BlanketOrderService.listAggregated(date, categoryId) + sumByCategory(date)
  → 读 daily_statistics + statistics_item（只读；未聚合返回空，由聚合任务生成）
GET /operation/blanket-orders/history（页面）或 GET /api/v1/operation/statistics/daily
  → BlanketOrderService.pageDailyStat(DateRange, PageQuery) → 按 statistics_date 倒序分页
```

### 5. 生产单打印

```
页面 /operation/blanket-orders/print/preview（新窗口）或 POST /api/v1/operation/blanket-orders/print
  → BlanketOrderService.printProductionOrder(date, categoryIds, PrintFormat)
  → BlanketOrderServiceImpl
       1) requireWindowClosed（截止前不能打印）
       2) 无快照则先 rebuild 一份
       3) 按 categoryIds 过滤明细
       4) TXT/PRINT → 文本生产单；XLSX → SpreadsheetML 表格；PDF 未实现 → 40001
  → OperationExportSupport 统一命名下载（Content-Disposition）
```

页面侧 `/operation/blanket-orders-print.html` 是独立的纸质排版页（内联样式，`window.print()`）。

### 6. 配送任务生成（配餐开始后，幂等）

```
定时任务 11:30 DeliveryOpenJob → DeliveryService.generateTasks(date, null, null)
页面「生成配送任务」POST /operation/deliveries/generate 或 API POST /api/v1/operation/deliveries/generate
  → DeliveryService.generateTasks(date, deptId, workstation)
  → DeliveryServiceImpl
       1) requireDeliveryOpen：取 ServiceWindowService.get(...).deliveryStartTime 与服务器时间比较，
          未到配餐开始时间 → 42201 OUT_OF_TIME_WINDOW；历史日期视为已开放（允许补派单）
       2) OrderQueryService.listValidByDate(date) → 当日有效订单
       3) UserService.listByIds 补员工姓名/工位/电话
       4) groupByEmployee（可按 deptId / workstation 过滤）
       5) 已存在任务的员工跳过（statistics_date + employee_id 唯一约束兜底）
       6) buildTask：task_no = DT-yyyyMMdd-序号，明细来自订单快照 → 保存 delivery_task + delivery_task_item
       7) 发布 DeliveryGeneratedEvent(date, taskIds, count)
```

### 7. 配送列表 / 详情 / 状态流转

```
GET /operation/deliveries（页面）→ DeliveryService.page(DeliveryQuery)
  → DeliveryServiceImpl.page：Specification（日期/状态/工位/部门/员工）下推数据库分页，按 task_no 升序 → enrich 员工信息
GET /operation/deliveries/{id}（页面）→ getDetail(taskId)
POST /operation/deliveries/{id}/status 或 PUT /api/v1/operation/deliveries/{taskId}/status
  → DeliveryService.updateStatus(taskId, status, receiver, remark)
  → TaskStatus.canTransitionTo：PENDING→DELIVERING→DELIVERED；任一步可转 EXCEPTION；非法流转 40902
  → 已送达/异常时写 delivered_at；保存打印次数之外的签收信息
```

### 8. 批量打印配送单

```
页面勾选任务 → POST /operation/deliveries/batch-print（打印页）
或 API POST /api/v1/operation/deliveries/batch-print
  → DeliveryService.batchPrint(taskIds, templateId)
  → DeliveryServiceImpl
       1) 校验 taskIds 非空、任务都存在
       2) 每张任务 markPrinted(now)：print_count++、printed_at=now（审计重复打印）
       3) renderBatch：按员工/工位渲染配送单文本 → PrintBatchVO(printBatchId, printedCount, content)
  → 打印页 deliveries-print.html（内联样式）
```

### 9. 配送台账导出

```
GET /api/v1/operation/deliveries/export → DeliveryService.export(date, deptId, ExportFormat)
  → 14 列台账（任务号/员工/工位/电话/明细/状态/打印次数/签收…）→ OperationExportSupport（XLSX/CSV）
```

### 10. 定时任务与事件（`config/OperationScheduleConfig`）

| 触发 | 任务 | 动作 |
| --- | --- | --- |
| 每天 09:00 `0 0 9 * * ?` | `OrderWindowCloseJob` | 发布 `OrderWindowClosedEvent` → `OrderWindowClosedListener`（`fallbackExecution=true` + `REQUIRES_NEW`）→ `aggregate(date, true)` |
| 每天 11:30 `0 30 11 * * ?` | `DeliveryOpenJob` | `DeliveryService.generateTasks(today, null, null)` |
| 订单创建（M2 事件） | `OrderCreatedListener`（AFTER_COMMIT + `REQUIRES_NEW`） | `BlanketOrderService.refreshDailyStat(date)` 重算当日快照（幂等覆盖写） |
| 订单变更（M2 事件） | `OrderUpdatedListener`（AFTER_COMMIT + `REQUIRES_NEW`） | `BlanketOrderService.refreshDailyStat(date)` 重算当日快照（幂等覆盖写） |

> 定时任务只是“兜底 + 幂等”：真正的取值时间来自 `service_window`，聚合与派单都可以重复执行。
>
> 注意：定时任务的 cron 是固定的 09:00 / 11:30，而实际截止/配餐时间来自 `service_window`。
> 若把配置改到 09:00 之后，当天的 09:00 聚合会因“未到截止时间”抛 42201（`DeliveryOpenJob` 有
> try/catch 只记日志，`OrderWindowCloseJob` 的异常会由调度器记录）。
> 这不影响正确性——当天的快照已由 `OrderCreatedListener` / `OrderUpdatedListener` 保持最新，
> 只是少了“截止这一刻的强制重算”。

## 六、跨模块依赖与事件

| 方向 | 对象 | 用途 |
| --- | --- | --- |
| 调用 M2 | `OrderQueryService.listValidByDate(date)` | 聚合与派单的订单来源（只读，不碰订单表） |
| 调用 M4 | `UserService.listByIds(ids)` | 配送单补工位/电话 |
| 被 M2 调用 | `ServiceWindowService.get(date, scope, deptId)` | 下单校验截止时间（唯一时间来源） |
| 被 M2/M3 共用 | `RecipeService.listCategories`（M1） | 生产单按分类聚合时解析分类 |
| 订阅事件 | `OrderCreatedEvent`、`OrderUpdatedEvent` | 下单 / 改单 / 取消 / 作废后重算当日 `daily_statistics` 快照（`refreshDailyStat`，幂等覆盖写） |
| 订阅事件 | `OrderWindowClosedEvent` | 定时聚合：`aggregate(date, true)` 强制覆盖重算（`fallbackExecution=true`，因为定时任务发布事件时没有事务） |
| 发布事件 | `DeliveryGeneratedEvent` | 打印/通知类扩展点（当前无订阅方） |

## 七、关键不变量

1. **聚合时机**：只在订餐截止后汇总当日 PENDING/VALID 订单（截止前 42201）。
2. **配送时机**：只在配餐开始后生成配送单（未到时间 42201）。
3. **两者都幂等**：聚合按 `statistics_date` 覆盖写；派单按 `(statistics_date, employee_id)` 跳过已存在的员工。
4. **快照只读**：`daily_statistics` / `delivery_task` 的明细来自订单快照，不随菜品改价变化。
5. **时间窗口单一来源**：任何“能不能下单/配送”的判定都调 `ServiceWindowService.get`，不读配置常量兜底之外的值。
6. **状态机**：配送状态只能按 `TaskStatus.canTransitionTo` 流转，不允许跳跃与回退。

## 八、验证方式

- 自动化用例：`.\gradlew.bat test --tests "*WindowClosedAggregationTests" --console=plain`
  （无事务的定时任务入口 + 覆盖掉人为写脏的快照）。
- dev 启动后：`kitchen/kitchen123` 登录 → `/operation/blanket-orders`；把时间窗口调到凌晨（`manager` 在 `/operation/configs/service-window`）
  即可让“聚合/派单”前置条件成立，手动聚合并生成配送；`delivery/delivery123` 登录打印配送单。
- 边界：截止前聚合应 42201；未到配餐时间派单应 42201；重复聚合 `force=false` 返回同一快照；
  重复派单只补新增员工；非法状态流转应 40902。
